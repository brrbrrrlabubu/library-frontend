# Полный аудит frontend онлайн-библиотеки Libra

**Дата аудита:** 15 ноября 2026 г.
**Объект:** frontend-проект `library-frontend` из предоставленного ZIP-архива.
**Результат:** выполнен полный аудит исходников и фактических запусков (`npm run build`, `npm run lint`, `npm run test`, `npm run format:check`), а также живой smoke-тест всех маршрутов в headless-браузере (гость, студент, администратор, guard-ы, страницы ошибок). Устранены все обнаруженные дефекты, включая два функциональных бага, найденных при проверке поведения в браузере (статусы просрочки в mock-режиме и навигация PDF-читалки). Вёрстка переведена на Mobile First с попиксельной проверкой эквивалентности. Все проверки качества проходят без ошибок и предупреждений, консоль браузера чистая.

## 1. Итоговый вердикт

Проект реализует весь обязательный блок ТЗ: публичный каталог с поиском/фильтром/сортировкой/пагинацией, страницу книги по QR-коду, вход по JWT с обработкой 401 и блокировкой, кабинет студента с подсветкой сроков и штрафами, онлайн-чтение PDF, дашборд и CRUD-разделы администратора (книги, категории, студенты, выдачи и возвраты, должники, оплата штрафов), защищённые маршруты по ролям, 403/404, валидацию форм, тосты, лоадеры, пустые состояния, debounce поиска и модальные подтверждения. Из бонусов выполнены TypeScript, тёмная тема, unit-тесты и демо-график дашборда в mock-режиме.

В этой версии исправлены критические дефекты сборки и тестовой инфраструктуры, мёртвый код, ошибки локализации и каскада CSS, а также два runtime-дефекта: неверная передача аргументов в `Array.prototype.map` (из-за неё просроченные выдачи подсвечивались зелёным) и неработающая в Chromium навигация PDF-просмотрщика. Проект собирается, линтуется и проходит тесты без ошибок.

## 2. Исправления, внесённые в этой версии

### 2.1. Production-сборка падала (критично)

**Проблема:** `npm run build` завершался ошибкой TS2769 в `vite.config.ts`. `defineConfig` импортировался из `vitest/config`, а плагин React — из верхнеуровневого Vite 6; Vitest 2.1.8 тянул собственную вложенную копию Vite 5, и их типы были несовместимы. Проект нельзя было собрать и сдать.

**Исправление:** Vitest обновлён до 3.x (peer-зависимость Vite `^5 || ^6` — вложенная копия исчезла), конфиг переписан по официальному рецепту Vite 6: `/// <reference types="vitest/config" />` + `defineConfig` из `vite`.

### 2.2. Тесты падали (критично)

**Проблема:** `npm run test` завершался `ReferenceError: expect is not defined` в `test-setup.ts`: типы `vitest/globals` были подключены в tsconfig, но `globals: true` в конфигурации Vitest отсутствовал, и `@testing-library/jest-dom` не видел глобальный `expect`.

**Исправление:** в `vite.config.ts` добавлен `test.globals: true`. Попутно исправлен латентный баг `-0`: `Math.ceil` малого отрицательного дробного остатка возвращал `-0` в `daysRemaining`, что ломало строгие сравнения в тестах; значение нормализуется к `0`.

### 2.3. Вёрстка переведена на Mobile First (обязательное требование ТЗ)

**Проблема:** базовые стили описывали настольную раскладку, мобильные правила добавлялись через `@media (max-width: ...)` — прямое несоответствие обязательному пункту ТЗ «Mobile First». Предыдущая версия аудита признавала это ограничение.

**Исправление:** `styles.css` перестроен автоматически (скрипт с полным разбором каскада):

- база теперь описывает мобильную раскладку (≤390px);
- настольные стили подключаются тремя блоками `@media (min-width: 391px | 761px | 1051px)`;
- шорткаты (`padding`, `margin`, `border`, `background`, `flex`, `gap`, `grid-column`, `overflow`, `border-radius`) канонизированы в лонгхенды перед слиянием, чтобы взаимодействие шорткат/лонгхенд совпадало с реальным каскадом браузера;
- свойства, существующие только на мобильных, сбрасываются через `revert`;
- три селектора (`.brand`, `.section-top h2`, `.section-block`) сохраняют переопределения в `max-width`-блоках: они конкурируют с равными по специфичности селекторами (`.footer-brand`, `.profile-section h2`, `.section-latest`), и перенос их значений в `min-width`-блоки менял победителя каскада;
- CSS отформатирован Prettier'ом и снабжён документирующим заголовком.

**Проверка эквивалентности:** выполнено сравнение «до/после» в одинаковом окружении (headless Chromium, заблокированные внешние картинки/шрифты, скрытые скроллбары):

- computed styles всех элементов на 29 комбинациях «страница × ширина» (1440/900/768/375px, страницы: главная, каталог, карточка книги, QR-страница, вход, кабинет, все админ-разделы, 404) — различий нет;
- `getBoundingClientRect` всех элементов на тех же комбинациях — различий нет;
- попиксельное сравнение скриншотов (подмена CSS в той же странице) — 21/21 идентичных.

### 2.11. Просроченные выдачи подсвечивались зелёным (критично, runtime)

**Проблема:** в `src/api/mock.ts` функции снапшота передавались в `Array.prototype.map` как `loans.map(mockLoanSnapshot)`. В JavaScript такой вызов forwarding’ает **индекс элемента** вторым аргументом, а `mockLoanSnapshot(loan, now = Date.now())` принимает его как текущее время. Для первой выдачи `now = 0` (эпоха), для второй — `1` мс. Из-за этого ни одна выдача никогда не получала статус `OVERDUE`, а `daysRemaining` превращался в ~20 000 дней: в кабинете студента, админ-выдачах, карточке студента и «последних выдачах» дашборда просрочка с штрафом показывалась зелёным «В срок». Это ломало обязательное требование ТЗ о красной подсветке просрочки в демонстрационном (mock) режиме, на котором проходит сдача.

**Исправление:** явные стрелочные обёртки `map((loan) => mockLoanSnapshot(loan))` во всех четырёх местах (`getLoans`, `getDebtors`, `getMyLoans`, `getDashboard`) с поясняющим комментарием. Добавлен регрессионный тест `src/api/mock.test.ts`: seeded-выдача со просроченным сроком обязана приходить со статусом `OVERDUE`, `daysRemaining` обязан быть в разумном диапазоне, должник обязан иметь ненулевой неоплаченный штраф.

**Проверка в браузере:** кабинет студента показывает «Мастер и Маргарита» (срок 9 дней назад, штраф 90 сом) красным «Просрочено», вкладка «Выдачи» администратора — статус «Просрочено» для той же выдачи.

### 2.12. Навигация по страницам и масштаб не работали в PDF-читалке (критично, runtime)

**Проблема:** `ReaderPage` менял только URL-фрагмент `iframe` (`#page=N&zoom=X`). Chromium (а с ним Chrome/Edge — большинство пользователей) **не выполняет переход** при изменении только фрагмента у уже загруженного `iframe`, поэтому встроенный PDF-просмотрщик оставался на первой странице: поле «Страница» и кнопки масштаба визуально ничего не делали. Это нарушало обязательное требование ТЗ «Навигация по страницам, масштаб».

**Исправление:** `iframe` получил `key={pdfViewerUrl.toString()}` — при смене страницы/масштаба React пересоздаёт фрейм, и PDF гарантированно открывается на запрошенной странице с нужным масштабом во всех браузерах.

**Проверка в браузере:** после установки страницы 5 фиксируется повторная загрузка документа во фрейме (network log), URL фрейма содержит `#page=5`.

## 6. Ограничения и условия подключения к backend

- OpenAPI/Swagger документация backend не прилагалась: маршруты и DTO в `src/api/services.ts` — типовой контракт, сверить с фактическим API и адаптировать в API-слое.
- Для подсветки сроков backend должен возвращать `status` и `daysRemaining`; сумма штрафов (`unpaidFineTotal`) и сводка должников считаются на сервере.
- Загрузка файлов — `multipart/form-data` (`coverFile`, `pdfFile`), имена полей сверить с документацией.
- График выдач в real-API режиме требует endpoint со статистикой по периодам.
- GitHub-репозиторий и URL деплоя заполняются студентом перед сдачей.
